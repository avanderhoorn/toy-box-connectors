# Links

Links hold the owner's settings for each Toy Box channel's Slack connection: which Slack channel it watches and who may make requests.

## Domain model

A link binds one Toy Box channel to one Slack channel, through the app whose bot reads and answers there, and lives in that app's `bridge.db`. A Toy Box channel links through at most one app, and a Slack channel links to at most one Toy Box channel in each app, so leads that share a Slack channel each answer as their own app's bot. Its allowlist names Slack people by exact user ID, and only they can make the lead act. Request mode is `mention` by default or `all`, and observe mode is `requesters` by default or `channel`. It keeps its channel's audience as the owner approved it, and the bridge suspends it when Slack makes continuing unsafe.

## Boundaries and invariants

- Only the owner widens access. `link`, `allow` and `resume` first answer with what they'd widen, in names from Slack, and change something only when a call brings the owner's passphrase and the name of what it was shown, a hash of that preview. The bridge checks the passphrase against the argon2id hash in `credentials.env`, read at each check, and builds the preview again inside the write's transaction, so a change that's no longer what the owner saw is refused. `link` asks even when it only narrows, so no judgment of whether a change widens decides whether it's checked. `deny`, `pause` and `unlink` only narrow, so they apply at once, for the lead too: `deny` cancels what the person asked, and `unlink` deletes what the link kept.
- The owner chooses the passphrase at a terminal, never through the bridge. `serve` asks for it the first time it runs at one, and `passphrase` sets it again or changes it given the old one. Neither does so in a Copilot session, whose shell can be a terminal too: `serve` doesn't ask there, and `passphrase` refuses without saying what it checked, so a lead told that none is set passes that on instead of choosing one. A forgotten one means deleting its line from `credentials.env` and running `passphrase` again. There's no lockout, since only processes running as the owner reach the socket, and they can read the hash anyway. The passphrase stops a lead steered by Slack text from widening access through `toy-box-slack`, not a process that edits the bridge's files.
- `model/admission.ts` admits only a full member of the installation's workspace or Enterprise org, never a guest, a deactivated account, a bot or Slackbot, and refuses when users.info leaves out what it needs. `allow` asks Slack when it shows the owner whom it adds and again when they confirm. Nothing rechecks people once allowed, so someone Slack later makes a guest stays allowed until the owner denies them.
- `model/audience.ts` judges every read of a linked channel against the audience the owner approved, never against the read before it, so a widening, or a read that can't rule one out, suspends the link until the owner resumes it. Only an approved read lets the lead post there.
- `model/status.ts` names each suspension and what ends it, which `status` and `pause` say. A link whose Slack channel has a new ID ends only with unlink and a link to the new ID: `resume` refuses it, and so does `link` by either ID, before they ask Toy Box or Slack and again as they write, and no later suspension replaces that reason.
- A link's rows in `allowlist`, `cursors`, `wakes` and `outbox` cascade from it. Those in `requests` hold its ID and those in `messages` and `changes` its Slack channel's, with no foreign key, so `unlink` deletes them itself in the transaction that deletes the link. `request_messages` and a reply's `outbox` row cascade from `requests`. A person's name and other IDs in `users` stay only while some link allows them, so the bridge forgets them within an hour of the `deny` or `unlink` that ends that. Uninstalling the app or revoking its token deletes every row but the installation, which stays marked uninstalled so the bridge won't start again on tokens Slack revoked. No delete touches SQLite's own tables, so requests, changes, outbox items and gaps go on numbering after every one there has been.
