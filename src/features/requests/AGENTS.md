# Requests

Requests are how a Slack message becomes work for the lead and how that work gets answered. This guide follows the request loop end to end: classification and the request lifecycle here, waking the lead in `src/features/wakes`, and the CLI contract the lead answers through in `src/features/commands`.

## Classification and lifecycle

Classification is pure policy over a stored message, its thread, and its link's settings. It runs in the same transaction that stores the message, so a message and the request it opened or joined never disagree, and recovered messages are classified exactly like live ones. A request opens when an allowlisted person mentions the bot, posts a root message in a channel whose request mode is `all`, or follows up in a thread where they asked before. Eligibility comes from the allowlist, the link's modes, and the message's author, and bridge code decides it. The model is never asked whether someone may make a request, and messages from bots, apps, and the bridge itself never open one.

A request belongs to one link and one Slack thread and is shown to the lead as `r14`. Its number is never handed out again, even once its row is gone, so a number the lead still holds can't name a newer request. Its lifecycle is a state machine whose transitions are named pure functions. An edit or delete of its source updates the request instead of opening another. Slack withdrawing its source isn't its requester taking it back, so the request is revised without it and holds its replies until repair re-reads the source. A revision that arrives while a final reply is on its way gives the request back to the lead as updated, and a final still queued is superseded, since it answers what the request said before. A request that was dismissed, cancelled, or expired never reopens, so a new ask starts a new request.

## Waking the lead

Cancellation and expiry queue removal of the request's 👀 in the same transaction. A refused thread or a proved reply outside its intended thread cancels the request as `thread_gone` immediately, without waiting for withdrawal. Other failed final replies return the request to the lead with `reply_failed`.

The wake policy is a pure decision over a link's durable request state, the lead's presence, and the wake budget. The scheduler decides again whenever requests, presence or routines change, when the earliest wait ends, and at least every minute, and each pass first expires the requests that waited their lifetime without an answer. It wakes the lead privately by running a routine in Toy Box: the link's requests routine for requests, reminders and setup, or a publication series' routine to catch up a missed period. Each wake's kind and outcome are recorded with what the wake changed in one transaction, so a restarted bridge keeps its backoff. It never wakes the lead without durable work waiting, never exceeds the budget, and runs one routine per Toy Box channel at a time, holding the channel until the turn it started shows in presence. While the bridge can't use Slack, wakes wait for it, because a woken lead couldn't act, and the Toy Box client keeps following each linked channel. A wake that inbox didn't follow backs off and then stalls until new work arrives, held requests get no reminders, and a missed publication is caught up once, not once per missed period.

## The CLI contract

The lead answers through `toy-box-slack`, which sends versioned JSON over the bridge's Unix socket. Each command has zod input and output schemas, a pure Markdown presenter, and a documented exit code, and `--json` prints the same result as data. Output opens with a health banner and ends with the next step. The bridge resolves who is calling: the linked channel's lead may run everything, a member may only read, and any other session is refused. With no session, the caller is the operator, who may read and run setup but never reply or publish. While the bridge can't use Slack, because Slack hasn't said hello yet in this run or a token is missing, rejected or refused, it runs only the commands that need nothing from Slack, such as `status` and the commands that narrow. It refuses the rest with what's wrong, how to fix it and what the caller may still run, and a reconnect doesn't count, because posts wait for it. The CLI never talks to Slack or Toy Box itself and keeps no state of its own.

A command line names its command first, and parsing is strict, so a misspelled option is refused instead of ignored. The commands the CLI runs itself, such as `serve`, `install-skill`, `claim` and `reset`, are read the same way, but they take neither `--channel` nor `--json`. The CLI checks the input against the command's contract before it calls, so a mistake is caught even while the bridge is down. A command that takes text reads it from stdin when its option is missing, without the newline a heredoc ends with, and refuses empty text. The CLI exits 0 when the command ran, 2 when it couldn't reach a bridge, and 1 for anything else, which it explains. It prints Markdown on stdout when the command ran and on stderr when it didn't, and `--json` prints the bridge's answer, or an `{ "error" }` object, on stdout either way. The CLI waits a minute for an answer and the socket keeps a call open for two, so a slow command such as claim's wait is never dropped while the CLI still waits, and every command answers well within the minute. When the connection drops or the minute runs out, the command may or may not have run, so the CLI says to check `status` before running it again. A command that runs only as a step of another is served on the socket but has no command line of its own.

`inbox` is how the lead reads Slack. In one transaction it reports each of the channel's proposals that ended since it last did, shows each request that's new, changed or whose reply failed with every message the request holds, marks each read at the revision it showed, lists the requests the lead read and hasn't answered, reports once each one it read that was cancelled or expired since, with why but never what it said, and records the read, which ends the link's backoff. A result its contract would refuse rolls back, so nothing is marked read that didn't reach the lead. A request being answered waits on the outbox and isn't listed. Roles, names and files are read as they are now, so a requester the owner no longer allows shows as not allowed, the same check the outbox makes before it posts. Slack text is fenced and labeled with its author's role, its markup is rendered, and nothing in it can mention anyone in Toy Box: a person shows as `{Alice Chen}`, and an `@` gets a zero-width space after it, or becomes `%40` inside a URL so the link still opens.

`hold` and `dismiss` take a request as inbox shows it, such as `r14`, and act only on one of the caller's link that the lead has read and that still waits on its answer. Another link's request is refused the same way as one that doesn't exist. Each command checks and changes the request in one transaction and says why it refused in words the lead can act on, such as a request it hasn't read or one whose reply is already on its way. A hold stops reminders until the owner next posts in the Toy Box channel or the request changes in Slack, and a held request still expires. A dismissal quotes the revision the lead read, so it never closes a request over text that changed since. It posts nothing in the thread, cancels the replies still queued for the request, and takes back the 👀.

The skill in `skills/toy-box-slack` teaches the lead to work through the CLI: setup and approvals, answering requests, holds, digests, publishing, writing for Slack, what to trust, and restoring a waiting status. `toy-box-slack install-skill` replaces its folder in `~/.copilot/skills`, or in `$COPILOT_HOME/skills` when COPILOT_HOME is set, because that's where Copilot looks, and Copilot reads it when a lead's session starts or resumes. Its description names Slack work, so the leads of other channels don't load it. The skill only teaches: the bridge enforces every rule that matters and each routine prompt carries what its run needs, so a lead that never opened the skill still behaves. A test reads every command line the skill shows with the CLI's own grammar, so a renamed command or option fails the suite instead of misleading the lead.

## Boundaries and invariants

- A request's state changes only through its lifecycle functions, in the same transaction as the change that caused it.
- The [outbox](../outbox/AGENTS.md) owns delivery. A request isn't answered until its reply is delivered.
- [Toy Box](../toybox/AGENTS.md) runs the routine, and this loop decides when.
