# Requests

Requests are how a Slack message becomes work for the lead and how that work gets answered. This guide follows the request loop end to end: classification and the request lifecycle here, waking the lead in `src/features/wakes`, and the CLI contract the lead answers through in `src/features/commands`.

## Classification and lifecycle

Classification is pure policy over a stored message, its thread, and its link's settings. It runs in the same transaction that stores the message, so a message and the request it opened or joined never disagree, and recovered messages are classified exactly like live ones. A request opens when an allowlisted person mentions the bot, posts a root message in a channel whose request mode is `all`, or follows up in a thread where they asked before. Eligibility comes from the allowlist, the link's modes, and the message's author, and bridge code decides it. The model is never asked whether someone may make a request, and messages from bots, apps, and the bridge itself never open one.

A request belongs to one link and one Slack thread and is shown to the lead as `r14`. Its number is never handed out again, even once its row is gone, so a number the lead still holds can't name a newer request. Its lifecycle is a state machine whose transitions are named pure functions. An edit or delete of its source updates the request instead of opening another. Slack withdrawing its source isn't its requester taking it back, so the request is revised without it and holds its replies until repair re-reads the source. A revision that arrives while a final reply is on its way gives the request back to the lead as updated, and a final still queued is superseded, since it answers what the request said before. A request that was dismissed, cancelled, or expired never reopens, so a new ask starts a new request.

## Waking the lead

Cancellation and expiry queue removal of the request's 👀 in the same transaction. A refused thread or a proved reply outside its intended thread cancels the request as `thread_gone` immediately, without waiting for withdrawal. Other failed final replies return the request to the lead with `reply_failed`.

The wake policy in `src/features/wakes` is a pure decision over a link's open and seen requests and the routine runs the bridge attempted for it, because Toy Box's own wakes live in memory and fire at most once. A burst of new or changed requests earns one wake once it settles. A lead that leaves them unread is woken again after longer and longer waits, then left alone until something new arrives. A request the lead read and left gets one reminder unless the lead is woken first. A run Toy Box couldn't take retries with backoff, one it refused waits for something new, and no lead is woken more than 12 times an hour or while its link isn't active. The scheduler decides again whenever a request changes, after every run, when the earliest wait ends, and at least every minute, so a Mac that slept is noticed. Each pass first expires the requests that waited their lifetime, so nobody is reminded of them, and records each run's outcome, so a restarted bridge keeps its backoff. A storage error stops the bridge instead of retrying, so launchd restarts it.

## The CLI contract

The lead answers through `toy-box-slack`, which posts each call to the bridge's Unix socket with what its environment says about the caller. `commands/model/index.ts` declares each command as a spec: who may run it and a strict zod input. The CLI offers each input field as an option, or as an argument when it's positional, and forwards the text it read, and the bridge parses that text with the same schema, so a command can't mean one thing to the lead and another to the bridge. The bridge resolves the caller before anything else, so a caller it won't act for learns nothing about any channel. A session whose ID is a linked channel's is that channel's lead, a caller with no session is the owner at a terminal, who names a channel with `--channel`, and every other session, such as a member's, is refused. Any local process can set or unset the session variable, so roles stop mistakes rather than attacks, and the owner's passphrase is what stops widening.

The CLI exits 0 when the command ran, 2 when no bridge is running, and 1 for anything else, which it explains. It prints the command's Markdown on stdout when it ran and why it didn't on stderr, and `--json` prints the result, or an `{ "error" }` object, on stdout either way. It waits a minute for an answer. When the connection drops, the minute runs out or the bridge couldn't finish, the command may or may not have run, so the CLI says to check `status` before running it again. The CLI never talks to Slack or Toy Box itself and keeps no state.

`inbox` is how the lead reads Slack. In one transaction it lists the requests that wait on the lead, those it hasn't read first, each with every message its thread holds, and marks the ones it showed read, so a request past its limit, or one that changes meanwhile, waits for the next wake. Slack text is fenced and labeled with its author's role, so the lead can tell a request from text it shouldn't act on. Its markup is rendered, and nothing in it can mention anyone in Toy Box: a person shows as `{Alice Chen}`, and an `@` gets a zero-width space after it, or becomes `%40` inside a URL so the link still opens. `dismiss` takes a request as inbox shows it, such as `r14`, and ends it with the lead's reason. Another link's request is refused the same way as one that doesn't exist, and the lifecycle refuses a request the lead hasn't read as it stands. `status` shows Slack's connection and each link's settings, waiting requests and wakes, with what to do about anything that's wrong.

The skill in `skills/toy-box-slack` teaches the lead to work through the CLI. `toy-box-slack install-skill` replaces its folder in `~/.copilot/skills`, or in `$COPILOT_HOME/skills` when COPILOT_HOME is set, because that's where Copilot looks, and Copilot reads it when a lead's session starts or resumes. The skill only teaches: the bridge enforces every rule that matters, so a lead that never opened the skill still behaves.

## Boundaries and invariants

- A request's state changes only through its lifecycle functions, in the same transaction as the change that caused it.
- The [outbox](../outbox/AGENTS.md) owns delivery. A request isn't answered until its reply is delivered.
- [Toy Box](../toybox/AGENTS.md) runs the routine, and this loop decides when.
