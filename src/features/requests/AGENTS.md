# Requests

Requests are how a Slack message becomes work for the lead and how that work gets answered. This guide follows the request loop end to end: classification and the request lifecycle here, waking the lead in `src/features/wakes`, and the CLI contract the lead answers through in `src/features/commands`.

## Classification and lifecycle

Classification is pure policy over a stored message, its author's requests in its thread, and its link's settings. It runs in the same transaction that stores the message, so a message and the request it opened or joined never disagree. A request opens when an allowlisted person mentions the bot, posts a root message in a channel whose request mode is `all`, or follows up in a thread where they asked before, and their later messages there join it until the lead answers. Eligibility comes from the allowlist, the link's modes, and the message's author, and bridge code decides it. The model is never asked whether someone may make a request, and messages from bots, apps, and the bridge itself never open one. A thank-you or an okay never opens or joins a request, so it doesn't send the lead back to a thread it answered. A question never counts as one, even a lone `?` or `ok?`. While a link is paused, a requester's message still joins what they asked, so the lead reads it once the link resumes, but nothing new opens. A requester's history counts only before the message's own `ts`, so a message stored late classifies as it would have live.

A request belongs to one link and one Slack thread and is shown to the lead as `r14`. Its number is never handed out again, even once its row is gone, so a number the lead still holds can't name a newer request. Its lifecycle is a state machine whose transitions are named pure functions. A request is open until the lead reads it and seen after, answering once its reply is queued, and answered only once Slack confirms the reply, while a reply Slack refuses gives it back to the lead with `reply_failed`. An edit or a new message after the lead read a request flags it as updated, and the lead can't answer or dismiss it until inbox shows the change, so a reply never answers text the lead didn't read. Once its reply is on its way, edits change nothing. Deleting a request's source cancels it, and so does an edit that removes the mention it opened with. A request still waiting on the lead after seven days expires, and one whose reply is on its way doesn't. A request that was answered, dismissed, cancelled, or expired never reopens, so a new ask starts a new request.

## Waking the lead

The wake policy in `src/features/wakes` is a pure decision over a link's open and seen requests and the routine runs the bridge attempted for it, because Toy Box's own wakes live in memory and fire at most once. A burst of new or changed requests earns one wake once it settles. A lead that leaves them unread is woken again after longer and longer waits, then left alone until something new arrives. A request the lead read and left gets one reminder unless the lead is woken first. A run Toy Box couldn't take retries with backoff, one it refused waits for something new, and no lead is woken more than 12 times an hour. A paused or suspended link's requests wait, but a suspension wakes the lead once so it can tell the owner. The scheduler decides again after every command, whenever a request changes or the bridge suspends a link, after every run, when the earliest wait ends, and at least every minute, so a Mac that slept is noticed. Each pass first expires the requests that waited their lifetime, so nobody is reminded of them, and records each run's outcome, so a restarted bridge keeps its backoff. A storage error stops the bridge instead of retrying, so launchd restarts it.

## The CLI contract

The lead answers through `toy-box-slack`, which posts each call to the bridge's Unix socket with what its environment says about the caller. `commands/model/index.ts` declares each command as a spec: who may run it and a strict zod input. The CLI offers each input field as an option, or as an argument when it's positional, and forwards the text it read, and the bridge parses that text with the same schema, so a command can't mean one thing to the lead and another to the bridge. The bridge resolves the caller before anything else, so a caller it won't act for learns nothing about any channel. A session whose ID is a linked channel's is that channel's lead, a caller with no session is the owner at a terminal, who names a channel with `--channel`, and every other session, such as a member's, is refused. Any local process can set or unset the session variable, so roles stop mistakes rather than attacks, and the owner's passphrase is what stops widening.

The CLI exits 0 when the command ran, 2 when no bridge is running, and 1 for anything else, which it explains. It prints the command's Markdown on stdout when it ran and why it didn't on stderr, and `--json` prints the result, or an `{ "error" }` object, on stdout either way. It waits a minute for an answer. When the connection drops, the minute runs out or the bridge couldn't finish, the command may or may not have run, so the CLI says to check `status` before running it again. The CLI never talks to Slack or Toy Box itself and keeps no state.

`inbox` is how the lead reads Slack. In one transaction it lists the requests that wait on the lead, those it hasn't read first, and marks the ones it showed read, so a request past its limit, or one that changes meanwhile, waits for the next wake. So one long thread can't flood the lead, each request shows its thread's first message, its own messages and the newest 20 replies, with how many it left out between them, and inbox and activity cut a message after 4,000 characters, with how many they cut. A request's own messages always show, since reply waits until inbox has shown a change to any of them. Slack text is fenced and labeled with its author's role, so the lead can tell a request from text it shouldn't act on. Its markup is rendered, and nothing in it can mention anyone in Toy Box: a person shows as `{Alice Chen}`, and an `@` gets a zero-width space after it, or becomes `%40` inside a URL so the link still opens. `dismiss` takes a request as inbox shows it, such as `r14`, and ends it with the lead's reason. Another link's request is refused the same way as one that doesn't exist, and the lifecycle refuses a request the lead hasn't read as it stands. `status` shows Slack's connection and each link's settings, waiting requests and wakes, with what to do about anything that's wrong.

The skill in `skills/toy-box-slack` teaches the lead to work through the CLI. `toy-box-slack install-skill` replaces its folder in `~/.copilot/skills`, or in `$COPILOT_HOME/skills` when COPILOT_HOME is set, because that's where Copilot looks, and Copilot reads it when a lead's session starts or resumes. The skill only teaches: the bridge enforces every rule that matters, so a lead that never opened the skill still behaves.

## Boundaries and invariants

- A request's state changes only through its lifecycle functions, in the same transaction as the change that caused it.
- The [outbox](../outbox/AGENTS.md) owns delivery. A request isn't answered until its reply is delivered.
- [Toy Box](../toybox/AGENTS.md) runs the routine, and this loop decides when.
